## Probleem 6 — passlib/bcrypt versie incompatibiliteit

### Situatie
Bij de eerste seed-run werkte de admin-aanmaak niet. `passlib 1.7.x` is incompatibel met `bcrypt 4.1+` doordat bcrypt in versie 4.1 het `__about__` attribuut heeft verwijderd.

### Symptoom (volledige traceback)
```
(trapped) error reading bcrypt version
Traceback (most recent call last):
  File ".venv/lib/python3.10/site-packages/passlib/handlers/bcrypt.py", line 620, in _load_backend_mixin
    version = _bcrypt.__about__.__version__
AttributeError: module 'bcrypt' has no attribute '__about__'
...
ValueError: password cannot be longer than 72 bytes, truncate manually if necessary
```

### Oorzaak
`pip install passlib[bcrypt]` trok automatisch `bcrypt==5.0.0` binnen. `passlib 1.7.4` verwacht de oude `bcrypt.__about__.__version__` interface die in bcrypt 4.1+ is verwijderd.

### Oplossing
```bash
.venv/bin/pip install "bcrypt==4.0.1"
```

### Permanente fix in `requirements.txt`
```
# --- Auth ---
passlib[bcrypt]>=1.7.0
bcrypt==4.0.1  # passlib 1.7.x incompatibel met bcrypt 4.1+ (verwijderd __about__)
```

## Probleem 7 — score_type check constraint te restrictief

### Situatie
Van de 235 indicatoren in `indicatoren_seed.json` werden er bij de eerste seed slechts **65** geïmporteerd. De overige 170 werden stilzwijgend overgeslagen.

### Symptoom
```
⚠️ Overgeslagen Diversiteit Functies (Simpson Index): new row for relation "indicatoren" 
violates check constraint "indicatoren_score_type_check"
DETAIL: Failing row contains (..., index, ...)
```

### Oorzaak
De `indicatoren` tabel had de volgende CHECK constraint in `schema_latest.sql`:
```sql
score_type VARCHAR(10) DEFAULT '+/+' 
CHECK (score_type IN ('+/+', '+/-', '-/+', '-/-'))
```

Maar de seed JSON bevat ook de waarde `-=-` (gebruikt voor energielabels en index-indicatoren). Deze waarde was niet opgenomen in de constraint.

### Analyse van de seed JSON
```bash
grep -o '"score_type": "[^"]*"' init_data/indicatoren/indicatoren_seed.json | sort | uniq -c
# 226  "+/+"
#   5  "+/-"
#   3  "-/+"
#   1  "-=-"   ← ontbrak in constraint!
```

### Oplossing 1: Live DB fix
```sql
ALTER TABLE indicatoren DROP CONSTRAINT indicatoren_score_type_check;
ALTER TABLE indicatoren ADD CONSTRAINT indicatoren_score_type_check 
  CHECK (score_type = ANY (ARRAY['+/+', '+/-', '-/+', '-/-', '-=-']::varchar[]));
```

### Oplossing 2: Schema SQL permanent gefixt
In `init_data/schema/schema_latest.sql` regel 116:
```sql
-- VOOR:
score_type VARCHAR(10) DEFAULT '+/+' CHECK (score_type IN ('+/+', '+/-', '-/+', '-/-')),

-- NA:
score_type VARCHAR(10) DEFAULT '+/+' CHECK (score_type IN ('+/+', '+/-', '-/+', '-/-', '-=-')),
```

### Resultaat na fix
```
✅ 235 indicatoren geïmporteerd | 0 overgeslagen
```

## Probleem 8 — FastAPI/Starlette 1.0.0 breaking change

### Situatie
Na het starten van de server via `python run_dev.py` gaf de hoofdpagina (`/`) een **500 Internal Server Error**, terwijl de API-endpoints (bijv. `/api/gebiedsmonitor/gebieden`) gewoon werkten.

### Symptoom
```bash
curl http://localhost:8000/
# → Internal Server Error (HTTP 500)

curl http://localhost:8000/api/gebiedsmonitor/gebieden
# → 200 OK ✅
```

In de server-logs was te zien:
```
TypeError: unhashable type: 'dict'
```

### Geïnstalleerde versies (problematisch)
| Package | Versie |
|---------|--------|
| fastapi | 0.136.0 |
| starlette | **1.0.0** |
| uvicorn | 0.45.0 |

### Oorzaak
Starlette 1.0.0 is een **major release met breaking changes**. De interne verwerking van de `CORSMiddleware` en `BaseHTTPMiddleware` is gewijzigd. Specifiek: de manier waarop origins worden verwerkt en vergeleken is veranderd, waardoor een `dict` op een plek terechtkomt waar een hashable type verwacht wordt.

De app is ontwikkeld op een stabiele 0.x Starlette stack. De `pip install fastapi>=0.100.0` trok automatisch de nieuwste versie (1.0.0) binnen.

### Oplossing: Pinnen op stabiele versies
```bash
.venv/bin/pip install "fastapi==0.115.12" "starlette==0.41.3" "uvicorn[standard]==0.30.6"
```

**Bijkomend voordeel van `uvicorn[standard]`:** installeert automatisch `watchfiles` voor hot-reload, wat de `WARNING: --reload-include and --reload-exclude have no effect unless watchfiles is installed` waarschuwing oplost.

### Permanente fix in `requirements.txt`
```
# --- Web Framework ---
fastapi==0.115.12       # starlette 1.0.0 heeft breaking changes — pin op stabiele 0.115.x
starlette==0.41.3       # vastgezet — 1.0.0 breekt CORSMiddleware (unhashable dict)
uvicorn[standard]==0.30.6  # [standard] = watchfiles + httptools voor hot-reload
```

## Probleem 9 — Kompas hiërarchie koppeling (10 van 235 indicatoren)

### Situatie
Na de eerste correcte seed (235 indicatoren in DB) toonde het Kompas slechts **10 gekoppelde indicatoren**. De verwachting was dat het volledige Kompas met 12 thema's zichtbaar zou zijn.

### Symptoom (seed output)
```
🧭 STAP 3: Kompas hiërarchie laden
   ✅ Kompas geladen:
      Indicatoren gekoppeld: 10
      Indicatoren niet gevonden: 54
```

### Oorzaak
In `seed_fryslan.py` (regel 309) werd de koppeling gelegd via de kolom `Indicator SWF` uit de CSV:
```python
indicator_swf = row.get("Indicator SWF", "").strip()
if indicator_swf:  # ← deze kolom is bijna altijd LEEG
    cur.execute("SELECT uuid FROM indicatoren WHERE naam ILIKE %s", (indicator_swf,))
```

Maar de `kompas_hierarchie.csv` heeft de indicatornamen in de kolom **`Indicator`**, niet `Indicator SWF`. Die laatste kolom is in de meeste rijen leeg.

### CSV structuur (voorbeeld)
```
Title,Thema,Onderdeel,Indicator,Indicator actueel,Bron,Indicator SWF
Kwaliteit fysieke leefomgeving,Verkeer,veiligheid en overlast,Verkeersongevallen,N,,
Kwaliteit fysieke leefomgeving,Groen,Groene ruimte,Groen,J,,Groen
```

### Oplossing in `seed_fryslan.py`
```python
# VOOR (alleen Indicator SWF):
if indicator_swf:
    cur.execute("SELECT uuid FROM indicatoren WHERE naam ILIKE %s", (indicator_swf,))

# NA (Indicator als primair, Indicator SWF als fallback):
indicator_naam = row.get("Indicator", "").strip()
if not indicator_naam:
    indicator_naam = indicator_swf
if indicator_naam:
    cur.execute("SELECT uuid FROM indicatoren WHERE naam ILIKE %s", (indicator_naam,))
```

### Resultaat na fix
```
Indicatoren gekoppeld: 191  (was: 10)
Indicatoren niet gevonden: 33
```

## Probleem 11 — ON CONFLICT fout door dubbele alias-targets

### Situatie
Na toevoeging van de CBS-aliases gaf de batch insert een fatale fout:

### Symptoom
```
ERR: ON CONFLICT DO UPDATE command cannot affect row a second time
HINT: Ensure that no rows proposed for insertion within the same command 
      have duplicate constrained values.
```

### Oorzaak
Meerdere CBS-namen werden gemapt op **dezelfde DB-indicator**:
- `"Huishoudens met kinderen"` → `"Minima kinderen"`
- `"Huishoudens zonder kinderen"` → `"Huishoudens met laag inkomen"`
- `"Roker"` + `"Overmatige drinker"` → beide `"Roken"`
- `"In bezit overige verhuurders"` + `"In bezit woningcorporatie"` → beide `"Woningcorporatie bezit"`

Als voor dezelfde buurt (`gebied_id`) twee CBS-rijen dezelfde indicator-UUID kregen én hetzelfde jaar, zaten er duplicate `(gebied_id, indicator_uuid, jaar)` combinaties in één batch van 500 rijen. De PostgreSQL `ON CONFLICT DO UPDATE` verwerkt duplicates binnen dezelfde INSERT niet.

### Oplossing 1: Unieke alias-targets
De alias-mapping aangepast zodat overlappende CBS-namen naar **verschillende** DB-indicatoren wijzen waar mogelijk:
```python
"Huishoudens met kinderen":    "Minima kinderen",
"Huishoudens zonder kinderen": "Minima huish met kinderen",  # unieke target
"Personen met bijstand":       "Participatiewet totaal",     # unieke target
```

### Oplossing 2: Batch deduplicatie
Per batch dedupliceren op de primaire sleutel `(gebied_id, indicator_uuid, jaar)` vóór de insert:
```python
# Dedupliceer op (gebied_id, indicator_uuid, jaar) — voorkomt ON CONFLICT errors
seen = {}
for b in batch:
    key = (b[0], b[1], b[3])  # gebied_id, indicator_uuid, jaar
    seen[key] = b
deduped = list(seen.values())
# Vervolgens: execute_values(cur, INSERT ... , deduped)
```

### Resultaat na beide fixes
```
✅ 35.521 metingen geladen
⏭️  Overgeslagen (indicator onbekend): 2.188
❌ Fouten: 0
```
