# 0. Executive summary

De huidige D-OmniTwin-integratie gebruikt de 3DBAG REST API als backend-gedreven geometrieleverancier. De backend berekent een BBOX, haalt CityJSONFeatures op, decodeert CityJSON naar GeoJSON en retourneert uiteindelijk 2D-polygonen met hoogte-attributen.

Dat werkt als een pragmatische 2.5D-adapter, maar heeft een belangrijk nadeel: de D-OmniTwin-backend wordt afhankelijk van het schema, de paginering en de geometrische representatie van de 3DBAG API.

De gewenste architectuur verschuift daarom naar:

```text
3DBAG 3D Tiles
       ↓
Deck.gl / loaders.gl
       ↓
native client-side streaming
       ↓
3D rendering
       ↕
D-OmniTwin semantische data
       ↓
indicatoren / analyses / selectie / styling

De belangrijkste correctie op de eerdere blauwdruk is echter dat de voorgestelde Deck.gl-code met:

getFillColor: (...)

niet zonder meer geldig is voor Tile3DLayer.

De huidige Deck.gl-documentatie beschrijft voor Tile3DLayer geen algemene getFillColor accessor zoals bij GeoJsonLayer. Bij picking geeft Tile3DLayer volgens de documentatie bovendien een Tile3DHeader als info.object, niet automatisch een gebouw-feature met:

info.object.properties.identificatie

Daarom moet metadata, picking en data-driven styling als afzonderlijk technisch werkpakket worden gevalideerd.

De juiste architectuur is dus niet:

"3D Tiles + simpelweg getFillColor"

maar:

"3D Tiles als native streaminglaag + gevalideerde metadata/picking-laag + een expliciete stylingstrategie die aansluit op de feitelijke Deck.gl/loaders.gl-capabilities."

1. Visie & rol van 3D in de architectuur

Binnen D-OmniTwin moet worden gewaakt voor een "3D-first"-benadering.

Een gebouw is in de basis geen 3D-model, maar een semantisch data-object.

Architectuurprincipe

Data staat centraal; visualisatie is een afgeleide.

De 3D-geometrie is slechts één visualisatielaag van het semantische gebouwobject.

Alle koppelingen verlopen primair via de unieke BAG-identificatie.

BAG-ID
  ↓
Indicatoren / Sensoren / WOZ / Vergunningen / Context
  ↓
3D-geometrie
  ↓
Rendering via 3D Tiles

De geometrie is vervangbaar.

De identiteit en semantische relatie zijn dat niet.

2. Huidige situatie

De huidige bag3d.py implementeert grofweg:

Frontend
   ↓
POST /api/3dbag/buildings
   ↓
PostGIS
   ↓
BBOX EPSG:28992
   ↓
3DBAG REST API
   ↓
CityJSONFeatures
   ↓
Python CityJSON decoder
   ↓
GeoJSON Polygon
   ↓
Deck.gl

De router haalt onder andere:

BAG-identificatie;
oorspronkelijk bouwjaar;
status;
dakhoogte;
maaiveldhoogte;

uit de CityJSON-objecten.

De oorspronkelijke 3D-geometrie wordt vervolgens teruggebracht tot een GeoJSON Polygon.

Gevolg

De huidige oplossing is functioneel eerder:

3DBAG → 2D/2.5D webadapter

dan:

native 3D webstreaming.

Dit is voor een eerste implementatie verdedigbaar, maar niet de gewenste eindarchitectuur.

3. Waarom de huidige route kwetsbaar is
3.1 Backend is onderdeel van de geometriepipeline

De backend:

vraagt geometrie op;
decodeert geometrie;
transformeert coördinaten;
bouwt GeoJSON;
serialiseert de volledige response;
stuurt deze naar de browser.

Hierdoor ontstaan:

CPU-belasting;
memorygebruik;
extra latency;
extra payload;
serialisatiekosten;
parsingkosten;
onderhoud aan een eigen CityJSON decoder.
3.2 API-schema-afhankelijkheid

De huidige code gebruikt expliciet:

https://api.3dbag.nl/collections/pand/items

en verwacht bepaalde CityJSON-structuren en attributen.

De officiële 3DBAG-documentatie noemt de 3DBAG API momenteel nog niet OGC-compliant en beschrijft deze als CityJSONFeatures-service.

Daarmee is de REST API niet de meest robuuste primaire renderinglaag voor D-OmniTwin.

3.3 Eigen geometrische decoder

De functie:

_decode_cityjson_geometry(...)

is een eigen implementatie van CityJSON boundary decoding.

Dat introduceert een eigen onderhoudsoppervlak.

3.4 Paginering

De huidige implementatie begrenst het aantal pagina's en het aantal features.

Dat is bruikbaar voor snelle UI-respons, maar geen schaalbare streamingstrategie.

3.5 Server-side styling

De huidige backend verrijkt geometrieën met kleurinformatie.

Voor een interactieve 3D-viewer is dit niet de ideale scheiding van verantwoordelijkheden.

3.6 Concrete functionele kwetsbaarheid

Bij meerdere geselecteerde buurten kan de huidige buurtkleurverrijking dezelfde kleur op meerdere gebouwen toepassen, omdat na het ophalen van meerdere buurtwaarden uiteindelijk de eerste gevonden waarde als kleurbron kan worden gebruikt.

Dit moet bij migratie expliciet worden opgelost.

6. Belangrijke correctie: Deck.gl styling is geen simpele getFillColor

Dit is een van de belangrijkste gaps in de huidige blauwdruk.

Voor GeoJsonLayer bestaat bijvoorbeeld:

getFillColor

maar de huidige Deck.gl-documentatie voor Tile3DLayer biedt geen vergelijkbare algemene getFillColor accessor voor gebouwfeatures.

De gedocumenteerde Tile3DLayer-accessors zijn beperkter; onder andere getPointColor geldt voor point-cloud tiles, terwijl _getMeshColor expliciet als een beperkte/debuggerichte mogelijkheid voor mesh/I3S wordt beschreven.

Daarom is deze eerdere code:

const bag3dLayer = new Tile3DLayer({
  ...
  getFillColor: (tileFeature) => {
    ...
  }
});

niet als productie-implementatie aannemen.

Evenmin mag worden aangenomen dat:

info.object.properties.identificatie

automatisch beschikbaar is bij Tile3DLayer picking.

De Deck.gl-documentatie vermeldt dat info.object bij Tile3DLayer picking een Tile3DHeader kan zijn.

Ontwerpconsequentie

De styling- en pickingarchitectuur moet eerst empirisch worden vastgesteld.

7. Metadata: wel beschikbaar, maar toegang moet worden bewezen

3DBAG levert volgens de officiële documentatie metadata per gebouw via:

EXT_mesh_features
EXT_structural_metadata

Ook loaders.gl documenteert ondersteuning voor deze 3D Tiles/glTF-extensies.

Dit maakt semantische koppeling technisch veelbelovend.

Maar:

"3DBAG bevat metadata" betekent niet automatisch "Tile3DLayer geeft deze metadata als object.properties aan iedere accessor".

Dat is een cruciaal onderscheid.

Te bewijzen keten
3DBAG glTF
    ↓
EXT_mesh_features
    +
EXT_structural_metadata
    ↓
loaders.gl 3D Tiles loader
    ↓
Tile3D content / feature IDs
    ↓
Deck.gl Tile3DLayer
    ↓
picking / feature identification
    ↓
BAG-ID
    ↓
D-OmniTwin

Iedere stap moet afzonderlijk worden gevalideerd.

9. Mogelijke stylingstrategieën

Er zijn drie onderzoekspaden.

Strategie A — Native Tile3D styling

Onderzoeken of de gebruikte Deck.gl/loaders.gl-stack voldoende toegang biedt om:

feature ID
   ↓
feature metadata
   ↓
GPU color

rechtstreeks te implementeren.

Voordelen:

minimale extra geometrie;
ideale GPU-route;
volledige 3D-integratie.

Nadeel:

mogelijk custom Deck.gl-/shaderwerk nodig;
huidige standaard Tile3DLayer API is hiervoor niet voldoende bewezen.
Strategie B — Custom 3D renderinglaag

Onderzoeken of een aangepaste renderinglaag bovenop loaders.gl 3D Tiles mogelijk is.

Concept:

Tile3DLoader
     ↓
feature IDs + geometry
     ↓
custom rendering
     ↓
D-OmniTwin styling

Dit geeft maximale controle, maar verhoogt onderhoud en complexiteit.

Strategie C — 3D Tiles + gesynchroniseerde 2D data-overlay

Wanneer native feature styling te complex of te kwetsbaar blijkt:

3D Tiles
   +
2D BAG / MVT / GeoJSON

De 2D-laag kan dan de semantische kleur-/selectiecontext leveren terwijl de 3D Tiles de visuele massa renderen.

Dit is minder elegant dan volledig native 3D styling, maar kan als pragmatische tussenoplossing zeer performant zijn.

Niet vooraf kiezen. Eerst benchmarken.

10. Picking: expliciet ontwerpen

De gewenste gebruikersinteractie is:

Gebouw aanklikken
       ↓
feature identificeren
       ↓
BAG-ID
       ↓
D-OmniTwin detail

Maar Tile3DLayer picking moet hiervoor worden getest.

Acceptance criteria

Een klik op een gebouw moet:

een reproduceerbare feature-identiteit opleveren;
gekoppeld kunnen worden aan een BAG-ID;
onafhankelijk zijn van de huidige tile;
robuust blijven bij LOD-wisseling;
robuust blijven wanneer tiles unload/reload;
bruikbaar zijn voor hover;
bruikbaar zijn voor click;
niet afhankelijk zijn van geometrische centroidberekening.
Belangrijke hypothese

De metadata-/feature-ID-keten kan mogelijk worden gebruikt voor picking, maar dit moet in de concrete Deck.gl-versie worden bewezen.

24. 3DBAG-versiebeheer en recente servicebreuk

De officiële 3DBAG-downloadpagina toont momenteel de versie v20250903 als beschikbare release.

De officiële release notes beschrijven 2025.09.03 als de release waarin 3D Tiles v1.1 als nieuw outputformaat werd toegevoegd.

Backend CPU	hoog	laag
GeoJSON payload	groot	tile-gebaseerd
3D-geometrie	decode nodig	native
LOD	zelf regelen	tileset traversal
Caching	zelf bouwen	tile cache
Metadata	CityJSON	glTF metadata
Picking	eigen implementatie	tile/feature mechanismen onderzoeken
Styling	eenvoudig in GeoJSON	complexer, expliciet onderzoeken
Onderhoud	hoger	lager voor geometrie
Analyse	geschikt	niet primaire rol
Rendering	adapter	native streaming

Conclusie:

3D Tiles is de voorkeursroute voor rendering; REST/CityJSON blijft nuttig als data-/extractie-/fallbackroute.

42. Eindadvies

De migratie naar native 3D Tiles is architectonisch sterk en past beter bij D-OmniTwin dan de huidige CityJSON→GeoJSON-adapter.

Maar de migratie moet niet worden opgevat als:

REST API vervangen door Tile3DLayer

De echte migratie is:

Backend-gecentreerde geometrie
        ↓
native 3D streaming
        +
expliciete semantische koppeling
        +
expliciete feature picking
        +
gevalideerde stylingstrategie
        +
LOD / cache / memory management

De belangrijkste open technische kwestie is niet meer het laden van 3D Tiles — dat is relatief rechttoe rechtaan — maar:

Hoe ontsluiten we 3DBAG feature metadata/BAG-ID en hoe koppelen we die performant aan D-OmniTwin-indicatoren binnen de feitelijke Deck.gl Tile3DLayer-renderingpipeline?

Dat is het kernexperiment voor versie 2.

De architectuur moet daarom eerst een kleine maar diepgaande PoC doorlopen:

3DBAG LoD1.2
      ↓
Tile3DLayer
      ↓
metadata
      ↓
feature/picking
      ↓
BAG-ID
      ↓
D-OmniTwin lookup
      ↓
styling
      ↓
performance benchmark

Pas wanneer deze keten aantoonbaar werkt, moet de volledige 3D BAG-functionaliteit worden gemigreerd.
